# Agent Development Guidelines

## Purpose

This document defines the rules agents must follow when working on this project. The goal is to ensure that every implementation is based on the existing project structure, skills, utilities, design patterns, and animation systems instead of introducing unnecessary or inconsistent solutions.

## 1. Always Use the `skills` Folder

Before making any meaningful change, inspect the `skills` folder and all relevant files inside it.

### Required behavior

- Treat the `skills` folder as a source of project-specific knowledge and implementation guidance.
- Read all relevant skill files before starting implementation.
- If multiple skills are related to the task, inspect all of them instead of selecting only the first obvious match.
- Follow the patterns, conventions, utilities, APIs, and workflows defined by the skills.
- Do not recreate functionality that already exists inside the skills or project utilities.
- Do not ignore a relevant skill simply because an alternative implementation appears easier.
- If a skill references another file, utility, component, or workflow, inspect that dependency when it is relevant.
- Use the existing project architecture rather than introducing a parallel architecture.

## 2. Analyse the Existing Codebase First

Do not immediately start writing code.

Before implementation:

1. Inspect the project structure.
2. Inspect the `skills` folder.
3. Read relevant configuration files.
4. Locate existing components, utilities, hooks, animation helpers, styles, and shared patterns.
5. Identify how similar features are already implemented.
6. Reuse existing abstractions wherever possible.
7. Only then implement the requested change.

The agent should understand how the project works before modifying it.

## 3. GSAP and Animation Rules

When implementing animations, use the project's existing GSAP setup and conventions.

### GSAP requirements

- Inspect the `skills` folder for GSAP-specific guidance before writing animations.
- Inspect existing GSAP implementations in the project before creating new ones.
- Reuse existing animation utilities, hooks, timelines, plugins, and patterns.
- Use GSAP instead of introducing another animation library when GSAP is already the project's animation system.
- Use `gsap.context()` or the project's established cleanup mechanism where appropriate.
- Properly clean up animations, timelines, ScrollTriggers, and event listeners.
- Avoid creating animations directly inside render logic.
- Keep animation logic isolated from unrelated business logic.
- Prefer reusable timelines and animation utilities when the same behavior is used in multiple places.
- Avoid unnecessary `setTimeout`, `setInterval`, CSS transitions, or requestAnimationFrame implementations when GSAP already provides the required behavior.
- Register GSAP plugins according to the existing project pattern.
- Do not introduce duplicate plugin registration or duplicate animation initialization.
- Ensure animations work correctly when components mount, update, and unmount.
- Consider responsive behavior and reduced-motion requirements when the project supports them.

### GSAP quality

Animations should be:

- Intentional
- Smooth
- Performant
- Reusable
- Properly scoped
- Properly cleaned up
- Consistent with the existing visual language

Do not add animation merely because it is technically possible. Every animation should have a clear UX purpose.

## 4. Reuse Before Creating

Before creating a new:

- Component
- Hook
- Utility
- Helper
- Animation
- Style
- API abstraction
- Configuration
- Constant
- Type
- Data structure

check whether an equivalent or similar implementation already exists.

Prefer:

`Existing abstraction -> Extend it -> Reuse it -> Create new abstraction only when necessary`

Avoid:

`Create new implementation -> Duplicate existing behavior -> Introduce inconsistency`

## 5. Keep Code Clean

All code must be clean, structured, readable, and maintainable.

### Code quality rules

- Use clear and descriptive names.
- Keep functions focused on one responsibility.
- Keep components reasonably small.
- Separate concerns properly.
- Avoid deeply nested logic when it can be simplified.
- Avoid unnecessary abstractions.
- Avoid duplicated code.
- Avoid dead code.
- Avoid unused imports.
- Avoid unused variables.
- Avoid unnecessary dependencies.
- Follow the project's existing formatting and naming conventions.
- Preserve type safety where applicable.
- Handle errors intentionally.
- Keep files logically organized.

## 6. No Comments or Message Tags

Do not add comments to the code.

Do not add:

- Inline comments
- Block comments
- TODO comments
- FIXME comments
- Agent-generated explanations inside source files
- AI-generated message tags
- `AI:` tags
- `Agent:` tags
- `Generated by:` tags
- Temporary implementation notes
- Meta instructions inside source code

Code should communicate its intent through structure, naming, and architecture.

If something requires excessive comments to explain, simplify or restructure the implementation instead.

## 7. No Unnecessary Output

Do not add unnecessary files, wrappers, abstractions, dependencies, or configuration.

Every new addition should have a clear purpose.

Do not modify unrelated files.

Do not refactor large parts of the project unless the requested task genuinely requires it.

Keep the change set focused.

## 8. Follow Existing Project Conventions

The existing project is the source of truth for:

- Folder structure
- Naming conventions
- Component patterns
- Styling approach
- State management
- API structure
- Error handling
- Animation architecture
- Type definitions
- Testing patterns
- Build configuration
- Dependency usage

Do not impose a personal coding style when the project already has an established convention.

## 9. Use Existing Dependencies Properly

Before installing or introducing a dependency:

1. Check whether the project already has a dependency that solves the problem.
2. Check whether the `skills` folder specifies a preferred solution.
3. Check whether an existing project utility already solves it.
4. Only introduce a new dependency when it is genuinely necessary.

Do not add libraries for functionality that can reasonably be implemented with existing project tools.

## 10. Responsive and Accessibility Considerations

When working on UI:

- Check responsive behavior.
- Follow existing breakpoints.
- Preserve keyboard accessibility.
- Preserve semantic HTML.
- Avoid breaking focus behavior.
- Respect existing accessibility patterns.
- Support reduced motion when the project provides such behavior.
- Do not sacrifice usability for visual effects.

## 11. Performance

Performance should be considered during implementation.

Avoid:

- Unnecessary re-renders
- Excessive DOM manipulation
- Repeated expensive calculations
- Duplicate network requests
- Unnecessary animation loops
- Unbounded event listeners
- Uncleaned GSAP timelines or ScrollTriggers
- Large dependencies for small functionality

For animations, prefer GPU-friendly properties such as transforms and opacity when appropriate.

## 12. Validation Before Completion

Before considering a task complete:

1. Verify that the implementation follows the relevant `skills` guidance.
2. Check that existing patterns were reused where appropriate.
3. Check for unused imports and variables.
4. Check for type errors.
5. Check for linting or formatting issues.
6. Check animation cleanup.
7. Check responsive behavior for UI changes.
8. Check that unrelated functionality was not modified.
9. Verify that no unnecessary comments or message tags were introduced.
10. Verify that the final code is clean and structured.

## 13. Agent Decision Process

For every task, follow this sequence:

### Understand

Understand the requested behavior and constraints.

### Inspect

Inspect the project structure, `skills` folder, relevant files, existing implementations, and dependencies.

### Analyse

Determine the correct existing architecture, utilities, components, and patterns to use.

### Implement

Make the smallest clean implementation that satisfies the requirement.

### Integrate

Ensure the implementation fits naturally into the existing architecture.

### Validate

Check correctness, quality, performance, responsiveness, animation cleanup, and consistency.

### Finalize

Leave the codebase clean with no unnecessary comments, message tags, temporary code, or unrelated changes.

## 14. Core Rule

The agent must not treat the task as an isolated coding problem.

The agent must first understand the project's existing knowledge and architecture, especially everything relevant inside the `skills` folder, and then implement the solution using those established patterns.

The priority order is:

1. Existing project architecture
2. Relevant `skills` guidance
3. Existing utilities and abstractions
4. Existing dependencies and patterns
5. Clean, minimal implementation
6. New abstractions only when genuinely required

The final implementation must be production-quality, clean, structured, maintainable, and consistent with the rest of the codebase.

## 15. Mandatory GitHub Checks and Production Quality Validation

Before considering any task complete, inspect and follow all relevant configurations, workflows, and quality checks defined inside the `.github/` directory.

### GitHub Configuration and Workflow Checks

- Inspect all relevant files inside `.github/`, including GitHub Actions workflows, pull request templates, issue templates, code ownership rules, repository instructions, and other project-specific configurations.
- Identify all required CI/CD checks, build validations, linting rules, formatting checks, type checks, security scans, dependency audits, and automated tests configured by the repository.
- Follow existing branch protection requirements, repository rules, and pull request conventions wherever applicable.
- Ensure all applicable GitHub Actions workflows pass successfully for the changes being made.
- Never bypass, disable, remove, or weaken existing checks simply to make a build or pull request pass.
- If a check fails, identify the root cause, fix the underlying issue, and rerun the relevant validation.
- Do not claim that a check has passed unless it has actually been executed and its result verified.
- If a check cannot be executed locally or requires GitHub-specific permissions, report the limitation clearly and identify the remaining validation required.

### UI Alignment and Responsive Design Validation

For every UI-related change, ensure that the implementation is visually consistent, properly aligned, and responsive across supported screen sizes.

- Verify layouts on mobile, tablet, laptop, and desktop viewports.
- Ensure containers, grids, flex layouts, sections, navigation elements, buttons, forms, cards, images, and typography are correctly aligned.
- Prevent horizontal overflow, overlapping elements, clipped content, unexpected whitespace, broken layouts, and inconsistent spacing.
- Follow existing design tokens, spacing scales, typography, breakpoints, component variants, and styling conventions.
- Ensure images, videos, tables, dialogs, dropdowns, navigation menus, and other interactive elements adapt correctly to smaller screens.
- Verify that fixed, sticky, and absolutely positioned elements do not obscure content or interfere with interaction.
- Check hover, focus, active, disabled, loading, empty, error, and success states wherever applicable.
- Preserve semantic HTML, keyboard navigation, accessible focus indicators, appropriate contrast, and reduced-motion support.
- Ensure all interactive elements work correctly with touch input as well as mouse and keyboard input.
- Avoid introducing layout shifts, unnecessary animations, or performance regressions.

### Functional, Code Quality, and Regression Checks

- Verify that the requested functionality works as intended, including relevant edge cases and error states.
- Run the applicable tests, linting, formatting, type checking, production build, and other checks required by the project.
- Check for console errors, runtime exceptions, broken imports, missing dependencies, failed network requests, and incorrect API integrations where the available environment permits.
- Verify that existing functionality, routes, components, authentication, data handling, and integrations remain unaffected unless explicitly included in the requested change.
- Review the final changes for duplicated logic, unused imports, unused variables, dead code, unnecessary dependencies, and accidental modifications to unrelated files.
- Validate animations, event listeners, subscriptions, and other resources for proper initialization and cleanup.
- Check for security issues, exposed secrets, unsafe input handling, and unintended changes to permissions or configuration.
- Use existing project utilities and testing infrastructure rather than introducing unnecessary tools or parallel implementations.

### Final Acceptance Criteria

A task is complete only when:

1. The implementation follows the existing project architecture and all relevant files in the `skills/` directory.
2. Applicable `.github/` rules, workflows, and repository checks have been inspected and respected.
3. The requested functionality has been implemented and validated.
4. UI alignment, responsiveness, accessibility, and interaction behavior have been checked wherever applicable.
5. Relevant tests, linting, type checks, and production builds have passed, or any unverified checks have been explicitly reported.
6. No unrelated functionality, repository rules, or existing quality safeguards have been broken.
7. The final implementation is clean, maintainable, performant, and suitable for production.

**Core principle:** Never mark a task as complete merely because the code has been written or the page looks correct on one screen. Validate the implementation against the project's existing standards, GitHub checks, functional requirements, responsive behavior, and production build requirements before reporting completion.
